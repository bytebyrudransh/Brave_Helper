## 0. Locked Decisions

These are decided. If you want to change one, change it *here* before any code moves.

| Decision | Choice | Why |
|---|---|---|
| Product shape | **Local AI Studio** (frontend-first), agentic browser deferred to V2 | One product, one architecture. Bridge = V2. |
| Hero feature for Phase 2 | **RAG over local documents** | Exercises persistence + workers + embeddings + chat in one shippable feature. |
| Browser bridge (V2) | **Manifest V3 Extension** (Chrome/Brave) | Lighter than Electron, ships faster, no `BrowserView` lifecycle pain. |
| Language | **TypeScript** | Migrate files as we touch them. No mixed-mode for new files. |
| State | **Zustand** | Already proven in the reference scaffold. |
| Styling | **Tailwind v4** | Drop the hand-rolled CSS variables in `index.css`. |
| Inference (in-browser) | **Transformers.js** for embeddings + small models, **WebLLM** for LLM chat | Standard pattern for WebGPU/WASM. |
| Inference (heavier) | **Direct fetch to Ollama** from the browser. No Express proxy. | Set `OLLAMA_ORIGINS=*` (or specific origin) on the Ollama daemon. |
| Persistence | **IndexedDB** (via `idb` wrapper) | Chat history, RAG embeddings, model registry, settings. |
| Build/dev | **Vite** with COOP/COEP headers (per `browser-ai-reference/vite.config.ts`) | Required for SharedArrayBuffer / WebGPU workflows. |

## 1. The Five Phases

Each phase has a **definition of done** that is binary — either it's true or it isn't. No phase moves on until its DoD is green.

### Phase 1 — Stabilize (target: 1 week)

Goal: stop the bleeding. Remove the dead-end Puppeteer path. Get a clean foundation.

**Steps**
1. Delete `server.js`, `server.log`, `puppeteer-core` and `cors` from `package.json`. Remove `express`.
2. Rewrite `ollamaService.js` → `ollamaService.ts`:
   - Direct `fetch` to `http://localhost:11434/api/chat`.
   - `stream: true`. Yield tokens via async iterator.
3. Add Zustand. Create `src/store/index.ts` with one slice for chat (messages, streaming state, current model).
4. Migrate `App.jsx` → `App.tsx`. Lift the eight `useState` calls into the Zustand store. Drop prop-drilling.
5. Rip out `BrowserSection.jsx` entirely (it's the Puppeteer UI). Replace the two-pane layout with a single chat-first layout for now.
6. Add Tailwind v4. Delete `src/index.css`'s custom variables. Keep a thin `index.css` for resets only.
7. Add `tsconfig.json`, `vite.config.ts` with COOP/COEP headers, and `eslint` + `prettier` configs.
8. Document Ollama setup in `README.md`: install, pull a model, set `OLLAMA_ORIGINS`.

**Definition of done**
- `npm run dev` boots a single React+TS+Tailwind app with a working streaming chat against local Ollama.
- No `server.js`, no Puppeteer, no Express in the repo.
- Zero JS files in `src/` (all `.ts` / `.tsx`).
- Chat history is held in Zustand (not yet persisted — that's Phase 2).

### Phase 2 — Hero Feature: RAG over Documents (target: 2 weeks)

Goal: ship one differentiated feature end-to-end so the Studio has a reason to exist.

**Steps**
1. **Web Worker scaffold**. Port `useModelLoader` pattern from `browser-ai-reference/`. Define one message protocol: `load`, `progress`, `ready`, `infer`, `result`, `error`.
2. **Embeddings worker**. Load BGE-small (or similar) via Transformers.js inside a worker. Expose `embed(texts: string[]) → Float32Array[]`.
3. **Document ingest**.
   - Accept `.pdf` / `.txt` / `.md` upload.
   - Parse PDF client-side (`pdfjs-dist`).
   - Chunk (≈500 tokens, 50 overlap).
   - Embed all chunks via the worker.
   - Store `{ docId, chunkText, embedding, metadata }` in IndexedDB.
4. **Retrieval**. Cosine similarity in a worker. Return top-K chunks for a query.
5. **RAG chat flow**. On user message: embed query → retrieve top-K → inject into Ollama chat prompt as context → stream response → render with citation markers linking back to source chunks.
6. **Persistence**. IndexedDB schemas for: documents, chunks, embeddings, conversations, messages. Use `idb` for typed access.
7. **UI**. A "Documents" tab (list, upload, delete) and a "Chat" tab that lets you scope a conversation to one or more documents.

**Definition of done**
- User uploads a PDF, asks a question, gets a streamed answer grounded in retrieved chunks, and can click a citation to see the source text.
- Closing and reopening the app preserves documents and chat history.
- Embedding a 50-page PDF doesn't freeze the UI (workers doing their job).

---

### Phase 3 — Studio Polish (target: 1 week)

Goal: make it feel like a product, not a demo.

**Steps**
1. **Model manager**. UI to list locally available Ollama models, pull new ones (`POST /api/pull` streaming), set a default.
2. **Conversation management**. Sidebar with conversation list, rename, delete, search.
3. **Settings**. Theme (light/dark), default model, embedding model, chunk size, retrieval K.
4. **Command palette** (`Cmd+K`). Switch conversation, switch model, upload document, jump to settings.
5. **Empty states + error states**. What happens when Ollama isn't running. What happens when no documents are uploaded.

**Definition of done**
- A new user can open the app, see a clear empty state telling them what to do, install a model from inside the app, upload a doc, and chat with it — without reading docs.

---

### Phase 4 — In-Browser LLM (WebLLM) (target: 1 week)

Goal: deliver the "no server needed at all" mode for users without Ollama.

**Steps**
1. WebLLM worker. Load Llama 3.2 1B-Instruct (4-bit) on first use. Cache via Cache API.
2. Provider abstraction in the chat layer: `OllamaProvider` and `WebLLMProvider` implement the same streaming interface.
3. Settings: pick provider per conversation. Default to Ollama if reachable, else WebLLM.
4. Model loading UI: progress bar, size warning, WebGPU detection + clear fallback message.

**Definition of done**
- On a WebGPU-capable browser with Ollama not running, a user can still chat (slower, smaller model, but it works).

### Phase 5 — V2 Bridge: Browser Extension (deferred — gate behind shipping Phase 1–4)

Not part of V1.5. Listed here so the architecture choices above stay aligned with where we're going.

When V1.5 is shipped and stable:
- Manifest V3 extension with side panel.
- Content script extracts a structured `PageSnapshot` (headings, links, forms, ARIA tree, bounding boxes).
- Studio receives snapshots over `chrome.runtime` messaging.
- Typed `ProposedAction` schema. Visual highlight before execution. User confirmation for any destructive action.
- The Studio app and the Extension are two artifacts in the same repo, sharing types via a `packages/shared` workspace.

## 2. Minimum Production Rules (carried over from Gemini's plan)

These apply from Phase 1 onward and are enforceable in code review:

1. No silent destructive actions (submit, pay, delete) — V2 only, gated by confirmation UI.
2. No action without a visible target.
3. No unstructured DOM guessing — structured extraction or nothing.
4. No memory-only sessions — anything the user creates persists to IndexedDB.
5. No hardcoded local executable paths (no `/snap/bin/brave` style).
6. No `useState` in `App.tsx` for cross-component state — Zustand only.
7. No new `.js` / `.jsx` files. TypeScript or it doesn't merge.
