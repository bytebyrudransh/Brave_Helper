# V3.0 Plan — Modes, Vision, and Memory

## What this product actually is

**A summarization and research assistant that lives in your browser side panel.** Primary jobs, in order:

1. **Summarize the page you're on** and answer questions about it.
2. **Search the web** to enrich answers and cross-reference what you're reading.
3. **Recall** what you've read in the past — local memory across sessions.
4. **Autofill forms** from a local encrypted vault — secondary feature, opt-in.

V1 → V2 framed the product as a privacy-first vault wrapper. That framing was wrong. A summarizer with no internet access can only chew on the page in front of you — that's a 5-minute novelty, not a daily-use tool. **Internet access is a first-class feature, not a dangerous corner.** Vault and autofill are real but secondary; they get strict guardrails because they handle credentials, but they don't define the product.

## The core architectural principle: one-way internet

The extension is a **read-only filter between the user and the web.** This is the property that makes "privacy" non-negotiable without any ceremony, master passwords, or mode-switching theater.

**The model READS. The model does not WRITE.**

| Direction | Allowed | Not allowed |
|-----------|---------|-------------|
| Outbound HTTP | `GET` only — search queries, URL fetches | `POST`, `PUT`, `DELETE`, form submits, file uploads, API calls with user-data payloads |
| Tool surface | Read page, search web, fetch URL, screenshot, recall history | Send email, post to social, submit form to remote, upload file |
| Inputs to model | Page text, search results, fetched URLs, screenshots, chat history | (the model only sees what the user is already looking at) |
| Outputs from model | Text in the side panel | (no outbound transmission of user data) |

**Why "privacy" is no longer a marketing claim, it's a property of the architecture:**

- Search queries are user-typed text — same as typing into Google. Nothing private leaves that wasn't already going to.
- URL fetches are `GET` against public URLs. The request body is empty.
- The vault is **locked by default**. Even if the model wanted to leak credentials, it can't see them.
- There is no `POST` code path in the extension. There is no `sendEmail()`, `uploadFile()`, `postToAPI()` tool in the model's toolset. They simply do not exist.

This is the same shape as your conversation with me right now: you're reading what I produce, you can ask me to fetch things, but I'm not pulling data out of your machine. The asymmetry is the safety mechanism.

Privacy is a **byproduct of the architecture**, not a feature we sell. The honest pitch is:

- **Fast** (no network round-trip for inference)
- **No quotas, no bills, no account**
- **Works offline** for inference; uses internet only as a read-only research input
- **Yours** (model weights on your disk, can't be deprecated)
- **Privacy comes free** because there's no outbound channel for user data — not because we built encryption rituals on top.

## Summary
V2.0 shipped the local helper with vault, structured autofill, encryption, and history. It works, but two problems showed up in real use:

1. **It's slow.** Default model (Gemma 4 26B) eats ~14.8GB VRAM on a 16GB card. No headroom, CPU spillover, sluggish tokens.
2. **It's useless without the web.** Model can only summarize the current page. No web search means no cross-referencing, no follow-up research, no "what else has been written about this." That's a deal-breaker for a research tool.
3. **It has no memory.** Each chat is isolated. The model can't recall a page from yesterday.

V3.0 fixes all three. The product becomes a **research assistant that runs locally for inference but reaches the web for content**, with an opt-in vault for autofill on the side.

V3.0 is still:
- local-first by default
- unpacked in Brave
- confirmation-first for risky actions
- not published to a web store

## Why this version exists

Recruiters asked the right question: *"How is this different from any other local AI extension?"* The honest answer in v2.0 was "it has a vault." That's not enough.

V3.0 turns it into a real differentiator:
- **Tiered access modes** that are mutually exclusive at the architecture level
- **Vision via local multimodal models** (qwen2.5-vl, llava) so the model can actually see what the user sees
- **Local RAG over browsing history** so the model has real memory across sessions
- **Speed-mode model switching** so the helper is fast by default and smart on demand

Every new capability is gated by a user-visible mode. The defaults are private. The user opts into power.

## V3.0 goals
Build a helper that can:
- run fast on the user's hardware by default (sub-second responses for common tasks)
- switch between small / medium / large models based on the task
- capture and reason over screenshots locally
- search the web in an explicit, audited online mode that auto-locks the vault
- recall past pages, chats, and screenshots through local vector search
- show the user, at all times, exactly what the model can see

## The modes

V3.0 has one **default research mode** and one **locked-down autofill mode**. The vault and credentials are the only thing that requires special ceremony.

### Mode A — Research (default)
**This is the mode the product runs in 95% of the time.** All of these are enabled together:
- Page reading (current tab, after hard refresh)
- Web search (whitelisted providers, default DuckDuckGo + Brave Search)
- URL fetch (model can fetch a link the user pastes)
- Screenshots
- Memory recall (RAG over local history)
- Vault: **locked** (cannot read credentials)

The model can summarize the page, search the web for context, fetch URLs, look at screenshots, and recall past pages — all in a single conversation. There's no toggling between sub-modes for normal research work.

This is safe because the **vault is not unlocked**. The model has no access to passwords, profile data, or any credential. Even if the model "misbehaved" with web access, there's nothing sensitive to leak.

### Mode B — Autofill (opt-in, locked-down)
Entered only when the user clicks "Unlock vault" and enters the master password. While in this mode:
- Vault: unlocked
- Page reading: enabled (the form being filled)
- Web search: **disabled** (auto-cut on vault unlock)
- URL fetch: **disabled**
- Screenshots: still allowed (you might want to verify the form visually)

The user finishes the form, clicks "Lock vault," and returns to Research mode. Vault auto-locks after a configurable inactivity timeout (default 5 min) regardless.

### Why this split
Mutual exclusion only matters when one capability could harm another. The harm path here is: *vault contains credentials → web access could exfiltrate them → vault must be locked when web is on*. So we enforce that. Everything else (page reading, search, recall, screenshots) is composable and runs together by default — that's how a research tool should feel.

### Mode indicator
Side panel header shows the current mode prominently:
- 🟢 **RESEARCH** — default, web on, vault locked
- 🔴 **AUTOFILL** — vault unlocked, web off

That's it. Two states, two colors, no ambiguity.

## Product rules (carried from v2.0, extended)
- **All outbound HTTP from the extension is `GET` only.** No `POST`, no payloads carrying user data. Enforced at the fetch wrapper.
- No silent fill, submit, send, pay, or delete on web pages.
- No invented personal data.
- Every filled value shows its source.
- Screenshots only on explicit user trigger.
- Vault is locked by default. Unlocking requires explicit master password entry.
- Vault stays locked unless the user is actively in Autofill mode.
- The model has no tool to send, post, or upload anything. Those tools do not exist in the toolset.

## Scope

**In**
- Speed-mode toggle (Fast / Balanced / Smart) with live model swap
- Default context window cap (8k for chat, configurable for extraction)
- Page text truncation before model send (relevance-ranked)
- Vision model integration for screenshot reasoning
- Online mode with whitelisted search providers (DuckDuckGo, Brave Search)
- Local vector store for chat history and page snapshots
- Memory recall mode (RAG over history)
- Privacy audit panel (what the model has seen, when)
- Mode indicator in side panel header

**Out (deferred to v4)**
- Multi-step task automation with approval steps
- Voice input (Whisper integration)
- Cross-device sync (E2E encrypted)
- Form-field learning / personalized autofill suggestions
- Custom workflow canvas (XYFlow)
- LoRA fine-tuning on user writing style

## Main features

### 1. Speed mode toggle
Three preset profiles, switchable from the side panel header:

| Mode      | Default Model        | Size  | Context | Use case                          |
|-----------|----------------------|-------|---------|-----------------------------------|
| Fast      | `qwen3.5:9b`         | 6.6GB | 8k      | Chat, quick summaries, autofill   |
| Balanced  | `qwen3:14b`          | 9.3GB | 16k     | Page Q&A, form analysis           |
| Smart     | `gpt-oss:20b`        | 13GB  | 32k     | Deep extraction, complex reasoning|
| Code      | `qwen2.5-coder:14b`  | 9GB   | 16k     | Auto-engaged on dev/code pages    |

All four fit fully in 16GB VRAM (no spillover to system RAM). `gemma4:26b` is intentionally **not** the default — it spills and causes the slowness problem v3.0 is built to fix. It can still be picked manually as a "Heavy" override.

Optional experimental tier: `qwen3.6:35b-a3b` (23GB MoE, 3B active) with llama.cpp MoE offloading — backbone on GPU, experts in RAM. Defer until after Phase 1 ships.

Rules:
- Default is Fast.
- Switching mode swaps the model in Ollama and updates context window.
- Current mode is shown in the header.
- Per-task override is allowed via slash command (`/smart`, `/fast`).

### 2. Context window discipline
v2.0 sends full page text up to 285k context. v3.0 enforces:
- Default cap: 8k tokens for chat
- Page text is truncated to relevant sections before send:
  - Title, headings, first N paragraphs, visible form fields
  - Boilerplate (nav, footer, ads) is stripped
- User can override via `/extract full` for big jobs (auto-switches to Smart mode)

### 3. Vision capability
Add a local multimodal model for screenshot understanding.

Flow:
1. User triggers screenshot (existing `/takeSS` or button).
2. Extension captures visible tab via `chrome.tabs.captureVisibleTab()`.
3. Side panel shows screenshot inline.
4. User asks a question about it.
5. Image is sent to a vision model (`llava:7b`, ~4.7GB) running in Ollama.
6. Response streams back.

Storage:
- Screenshots saved to local IndexedDB with metadata (URL, timestamp, dimensions).
- Optional: attach screenshot to current chat session for follow-up questions.

Vision model is loaded on-demand (not always in VRAM). When user takes a screenshot, the chat model is unloaded and the vision model loads. After response, chat model can be reloaded if needed.

### 4. Web access (always-on in Research mode)
Web access is part of Research mode by default — not a separate mode.

Capabilities:
- **Web search** via whitelisted providers (default: DuckDuckGo, Brave Search). User can add more providers in Settings.
- **URL fetch** when the user pastes a link or the model decides it needs to fetch one (the latter requires user confirmation per request unless the domain is on the trust list).
- **Cross-page summary** — model can pull from current page + search results + fetched URLs in a single answer.

Rules:
- No background fetching. Every request is initiated by user prompt.
- Every fetch is logged in the audit panel (URL, timestamp, response size).
- Search results and fetched HTML are sanitized (scripts stripped, response size capped at 200KB) before being sent to the model.
- Web access is **automatically cut** the moment the user unlocks the vault (Mode B / Autofill). Re-enabled when vault locks.

### 5. Local RAG over history
Build a local vector store for memory recall.

Indexed content:
- Chat session summaries (auto-generated when session ends)
- Page snapshots (when user runs `/save`)
- Screenshot captions (when vision model describes one)
- Vault entries are **never** indexed — vault content stays in encrypted storage only

Tech:
- Embedding model: `nomic-embed-text` running locally via Ollama
- Vector store: ChromaDB embedded mode, or simple cosine search over IndexedDB if ChromaDB is too heavy
- Chunk size: 512 tokens with 64-token overlap

Memory recall mode (Mode 4):
- User asks: "what was that article about MoE I read?"
- Extension searches vector store, returns top-K matches
- Side panel shows clickable list of past pages/chats with snippets
- User picks one, model answers using that context

Indexing happens in the background after content is saved, never during active chat.

### 6. Privacy audit panel
New tab in the side panel: **Audit**.

Shows:
- Recent mode transitions (when, why)
- Outbound network requests (URL, timestamp, mode at time of request)
- Pages read by the model (URL, timestamp, token count sent)
- Screenshots captured (URL, timestamp)
- Vault unlock events (timestamp, duration of unlock)

Filters: last 1h / 24h / 7d / all.
Export: JSON dump for the user's records.
Auto-purge: configurable (default 30 days).

This is the killer feature. No commercial extension shows you this. It's also cheap to build because we already log most of this in v2.0 history.

### 7. Mode indicator in side panel
Header shows current mode with a colored pill:
- 🟢 OFFLINE + PAGE (default, green)
- 🔵 VAULT UNLOCKED (blue)
- 🟡 ONLINE SEARCH (yellow)
- 🟣 MEMORY RECALL (purple)

Clicking the pill opens a mode-switcher with explanations of each mode's permissions.

## Architecture

```
manifest.json
src/
  background/
    index.ts              service worker, mode state machine
  content/
    index.ts              page snapshot + form extraction + fill
                          (gated by current mode)
  sidepanel/
    SidePanel.tsx         chat, history, vault, audit, mode indicator
    ModeSwitcher.tsx      mode transitions UI
    AuditView.tsx         audit log view
    MemoryView.tsx        RAG recall UI
  lib/
    ollama.ts             local streaming chat (now with model swap)
    page.ts               sidepanel <-> content messaging
    vault.ts              encryption + vault access (locks on mode change)
    history.ts            persistence helpers
    vision.ts             multimodal model integration
    embeddings.ts         local embedding generation
    vectorstore.ts        local vector search
    search.ts             web search providers (DuckDuckGo, Brave)
    audit.ts              audit log writer
    mode.ts               mode state machine + transitions
  store/
    index.ts              messages, snapshot, vault, history, mode, audit
```

## Mode state machine

```
                ┌─────────────────────┐
                │ Offline + Page      │ ← default on extension load
                │ (vault locked)      │
                └──┬─────────┬────────┘
       unlock vault│         │ enable online
                   ▼         ▼
   ┌──────────────────┐   ┌──────────────────┐
   │ Vault Unlocked   │   │ Online Search    │
   │ + Page           │   │ (vault locked,   │
   │ (online: off)    │   │  page off)       │
   └──┬───────────────┘   └────┬─────────────┘
   lock vault                  │ disable online
      │                        │
      └────────────┬───────────┘
                   ▼
             back to default

       Memory Recall is reachable from any
       state, but entering it locks vault
       and disables online + page.
```

Transitions are explicit. No implicit fallbacks. Every transition writes an audit log entry.

## Safety guardrails (extended from v2.0)
- No fill without review.
- No password reveal without unlock.
- No send / submit / delete automation.
- No fake values for unknown fields.
- No screenshot capture without user action.
- **New:** No mode transition without user confirmation.
- **New:** Vault auto-locks on online mode entry — no exceptions.
- **New:** Active tab reading is hard-disabled in online mode at the content-script level (not just UI).
- **New:** Web search results are sanitized before being sent to the model (strip scripts, limit response size).
- **New:** Outbound URL fetches require user confirmation per request unless on whitelist.
- **New:** Audit log is append-only — entries cannot be edited, only purged after retention window.

## Why this is a differentiator

Most local AI extensions do one thing:
- Cloud-based extensions (ChatGPT for Chrome, etc.): cloud-only, data leaves device
- Local-only Ollama wrappers: private but isolated, no internet, no memory
- Browser-native AI (Brave Leo, etc.): fixed model, no user control

V3.0 stakes a unique position:
- **Local-first** by default
- **User-controlled mode tiers** with strict mutual exclusion
- **Vault-encrypted** with master password
- **Multi-model** with speed/intelligence trade-offs
- **Vision-capable** through local multimodal models
- **Memory-augmented** through local RAG
- **Fully audited** with a transparency dashboard

Each capability is gated. Each mode is explicit. Each privacy-relevant event is logged. The user is in control at every step.

## Setup
1. Load the unpacked extension in Brave.
2. Run Ollama locally with at least:
   - `qwen3.5:9b` (Fast)
   - `qwen3:14b` (Balanced)
   - `gpt-oss:20b` (Smart)
   - `qwen2.5-coder:14b` (Code, optional)
   - `llava:7b` (Vision)
   - `nomic-embed-text` (Embeddings)
3. Create a master password for the vault on first use.
4. Pick a default speed mode (defaults to Fast).
5. Configure the online mode whitelist (or leave defaults).

## Non-goals
- Replacing Brave's native UI.
- Replacing a mature password manager feature-for-feature.
- Public Chrome Web Store distribution.
- Cloud-based AI processing of any kind.
- Model fine-tuning in v3 (deferred to v4).
- Multi-step autonomous task execution (deferred to v4).

## Success criteria
- Fast mode produces first token in under 1 second on user's hardware.
- Mode transitions are visible, explicit, and never silent.
- Vault is provably locked during online mode (verified by audit log + UI state).
- Vision model can answer questions about a screenshot locally.
- Memory recall surfaces relevant past pages from a natural-language query.
- Audit panel shows a complete log of mode changes, network requests, and page reads.
- The user can articulate, in one sentence, what the model can see right now.

## Open questions
- Vision model VRAM trade-off: load on-demand (slow first use, low idle VRAM) vs. always-loaded (fast vision, less room for chat model). Default to on-demand; revisit after measuring user behavior.
- RAG store: ChromaDB vs. simple IndexedDB cosine search. Start simple, upgrade if recall quality is poor.
- Online mode default search provider: DuckDuckGo (no tracking, simple API) vs. Brave Search (better quality, requires API key). Default DuckDuckGo, allow user to add Brave.
- Whether to allow vault unlock and online mode simultaneously with very strict guarantees (e.g., model can only call search, not read tab). Current decision: no, mutual exclusion is simpler to defend.
